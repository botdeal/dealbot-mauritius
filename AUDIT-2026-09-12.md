## 2. Ce qui ne fonctionne pas ou reste incomplet

- **Usage réel sans catalogue impossible** : 0 marchand, 0 offre ; aucune fiche marchande réelle, aucun prix ni lien affilié réel à parcourir aujourd'hui. Les données contrôlées des tests ne constituent pas un catalogue.
- **Autopilot n'importe rien**, même si sa réponse annonce `mode:production`, `status:ready`, `next_stage:affiliate_source_connection`.
- Auth de bout en bout non validée : URLs autorisées, URL du site, délivrabilité, quotas SMTP, confirmation et récupération réelles restent à vérifier. L'API publique Auth ne révèle pas ces réglages ; aucun secret de dashboard n'a été demandé ni lu.
- Preview protégée par connexion Vercel ; l'audit navigateur s'arrête à cette protection. Le navigateur local renvoie ERR_BLOCKED_BY_CLIENT. Donc aucun rendu desktop/mobile réel ni parcours utilisateur complet ne peut être certifié.
- FR/EN partiel : contenus dynamiques souvent bilingues, mais navigation, formulaires, historique et plusieurs erreurs restent en français. Responsive présent dans le CSS (grilles, menus, tableaux défilants, modales) mais non validé visuellement.
- Admin des offres disponible ; gestion complète des marchands/catégories/publicités via Supabase, pas un back-office éditorial complet dans le site. Pas de tableau global des conversions/commissions. Contact = messages dans la boîte admin, pas emails. Consultation des 50 derniers messages sans pagination.
- Absence de notification email/push des alertes. Pas d'actualisation automatique des prix à partir d'une source. L'expiration masque les offres via RLS, mais aucune tâche ne met automatiquement leur statut à jour. Une page déjà ouverte peut conserver un ancien prix jusqu'au rechargement ; le tracking revalide néanmoins la période en base.
- Catalogue chargé côté client, limité à 10 000 lignes par table : ce n'est pas une architecture de recherche à grande échelle. Lectures personnelles sans pagination ; limites RPC non équivalentes à des quotas de stockage sur tous les accès directs aux tables.
- Recréation complète d'un projet neuf et restauration de sauvegarde non vérifiées : migrations additives seulement, pas de baseline initiale complète. Pas de workflow de tests/cron versionné dans l'arbre actuel.
- Conservation/purge des données, suppression/export de compte automatisés et supervision des incidents non implémentés. Le site propose une demande via contact ; sa prise en charge reste manuelle.

## 4. État exact de dealbot-sync avant Admitad

Fonction distante **ACTIVE, version 3**, verify_jwt=false avec authentification applicative `withSupabase({auth:'secret'})`. Le refus live des clés absentes/publiques/invalides est validé ; verify_jwt=false ne signifie donc pas que le endpoint est ouvert. Aucun appel avec secret valable n'a été effectué pendant cet audit : le précédent HTTP 200/ok:true reste un résultat historique, pas un nouveau test authentifié.

Le fichier distant a été récupéré sans changer son comportement et versionné dans `supabase/functions/dealbot-sync/index.ts`. **Aucun redéploiement Supabase n'a été effectué.** Les quatre nouveaux tests exécutent ce handler avec un middleware et une base simulés ; ils ne testent pas l'authentification réelle.

| Étape | Existe | Manque |
|---|---|---|
| Entrée | POST, auth secret, timestamps, JSON, cache no-store | Lecture du body ou d'un flux, contrat de source, limites de taille |
| Ingestion/validation/normalisation | Aucun traitement de source | Téléchargement/pagination, validation de prix/devises/dates/URLs, mapping catégories et disponibilités |
| Déduplication/idempotence | UNIQUE deals(merchant_id,external_id), slugs uniques en base | Identité par source, external_id obligatoire, upsert, reprise et replay ; NULL external_id ne déduplique pas |
| Marchands/offres | Tables, RPC admin et contraintes disponibles | Création/mise à jour automatique, provenance, conflits entre données manuelles et source |
| Prix/historique | Trigger DB à l'insertion/changement de prix/devise | Source de prix, fraîcheur, stratégie de devises et validation des anomalies |
| DealBot Score | Colonnes de score et saisie éditoriale | Algorithme documenté, versionné, testé ; aucun calcul exécuté par sync |
| Expiration | RLS et tracking contrôlent starts_at/expires_at | Réconciliation des offres disparues, date de dernière observation, expiration après import complet réussi |
| Affiliation | Champs URL et tracking de clics | Adaptateur, sous-identifiants d'attribution, suivi des conversions ; Admitad déconnecté |
| Erreurs/exécution | Catch, réponse 500, logs console, trois lectures de comptage | Journal durable, retries/backoff, verrou concurrent, timeout, checkpoints, alerting, métriques de rejets |
| Automatisation | Rien de planifié identifié dans les ressources inspectées | pg_cron absent, aucun cron Vercel dans vercel.json ni workflow Git versionné ; un ordonnanceur externe éventuel n'est pas vérifiable ici |

Test déterminant : un POST contenant une offre au handler simulé renvoie toujours received=0 et created=0 et ne fait que trois lectures. Les commentaires « production pipeline » décrivent une intention, pas un moteur. **Le système n'est pas techniquement prêt à recevoir Admitad en production.**
